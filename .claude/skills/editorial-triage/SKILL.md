Consumes the output of an editorial review (the saved run record of the `editorial-review` workflow, or a directory of version 3 findings files) and closes every finding with one move. The deterministic work (normalise, resolve anchors, gate rewrites, nominate claim changes, dedup, plan, apply) lives in `build-triage.sh` and `grade-triage.sh`; the judgment work (predicting the closing move for each cluster from the rubric) fans out to one `GRADER` per page. The outcome is written to `~/trade-imports-arch-workspace/.claude/workareas/editorial-triage/<run>/`: `calibration/grades/*.json` and `calibration/score.json`, then `closing/plan.md` (the report), `closing/plan.json` and, after the apply step, `closing/applied.json`. The pages change only in the apply step, in the docs working tree, and are never committed here.

**Bash call hygiene** - one command per Bash call; paths in the literal `~/trade-imports-arch-workspace/...` form. Full rules: [`agent-skills.md`](../../best-practices/skills/agent-skills.md).

The frame is closing, not opening. Every finding gets exactly one closing move: `R` remove, `C` correct, `W` reword, `K` keep one side, `O` record as open with an owner, `I` ignore for now, `T` tell me what to do. Removal is tried first, growth needs a heuristic that allows the growth, and no question is put to the user in chat. The rubric that defines the moves: [`assets/grading-rubric.md`](assets/grading-rubric.md). The record contract and every rule the helpers apply: [`assets/editorial-triage-schema.md`](assets/editorial-triage-schema.md).

| Trigger | Steps |
|---------|----------------|
| "triage the review", "triage the editorial review", "close the review" | Step 1, the workflow for Steps 2 to 6, then Steps 6 to 8, on the review's run record |
| "triage findings" | As above, on a findings directory (`--from-review`) |
| "editorial triage" | As above; ask which run if none is named |

## State

Canonical state is JSON under `~/trade-imports-arch-workspace/.claude/workareas/editorial-triage/<run>/` (gitignored): `findings.json`, `retains.json`, `triage.json`, `index.json`, `manifest.json`, `verification/`, `calibration/` and `closing/`. The markdown views (`closing/plan.md`, `calibration/round-<n>.md`) are regenerated by the helpers; never hand-edit them.

## Step 1: Name the run and its inputs

Establish: the review to triage (a run id such as `wf_f07b54c5-79b`, a run record path, or a directory holding `review/*.json` and `review/run.json` with `mode`, `intent` and `sourceHashes`); the state of the pages the reviewers read (`git -C <docs repo> status --short` shows uncommitted edits; pass `--commit` a label such as `e7cbdb0+edits` when the tree is dirty, so the manifest says what was reviewed); and a run slug for the workarea, `<docset>-<date>` (for example `ins-auth-2026-09-10`).

## Steps 2 to 6: Run the Triage Workflow

Run Steps 2 to 6 as one workflow, so the session launches the triage and reads one result instead of driving each spawn:

```
Workflow name: editorial-triage
args: {"run": "<run id or path>", "workarea": "~/trade-imports-arch-workspace/.claude/workareas/editorial-triage/<run>", "commit": "<label>"}
```

For a findings directory, pass `"review": "<directory>"` in place of `"run"`. A veto at the spot check is handled by hand as Step 6 describes (calibrate, re-grade the one page, re-plan with a new `--seed`); relaunching the workflow would re-grade every page. The workflow builds, spawns one `CLAIM_VERIFIER` per page the build names and re-spawns a page once when the rebuild still names it, grades every page and the set-wide clusters, then scores and plans with a spot check of 10. It never applies. Read its result:

- `stopped: "verification"`: the rebuild still names pages after one retry. Read the `lines` and continue by hand from Step 3.
- `stopped: "grading"`: a grader returned nothing, usually a dropped connection. Launch the workflow again: the build applies the verdicts already written, so only the graders run again.
- `stopped: null`: read `closing/plan.md` and continue at Step 6's spot check. `gradeCountMismatch` names a page whose grader did not grade every cluster; re-grade that page by hand (Step 4) and re-plan before the spot check.

Steps 2 to 6 below are what the workflow does, and the manual fallback when the workflow cannot run.

## Step 2: Build

```
bash ~/trade-imports-arch-workspace/.claude/tools/editorial-triage/build-triage.sh --from-run <run id or path> --dir ~/trade-imports-arch-workspace/.claude/workareas/editorial-triage/<run> --commit <label>
```

Read the summary lines it prints: records by source, clusters and duplicates collapsed, anchor rungs, the claims line (records nominated for claim verification, and how many are held as `missing` or `stale`), buckets. The result must be version 3, with `mode`, `intent` and `sourceHashes`; a build that stops with a message names the remedy (missing page, missing run record, a result that predates version 3, a page the review did not hash). Every nominated rewrite and deletion carries `claimShift: missing` and sits in `propose/unverified` until a verdict exists, unless a validation check discards it; a page whose hash has moved on since the review holds its records as `stale`. The build's last lines name the pages to verify. The buckets only stratify the calibration sample; the closing move comes from the grader.

## Step 3: Verify claims

Spawn one `CLAIM_VERIFIER` per page the build names in its "spawn CLAIM_VERIFIER for" line, all in one message; a page the build reports as moved on gets no verifier, because its records stay stale until the review is re-run. The verifier judges every nominated rewrite and, on the same pass, every removal a record proposes of its own (a `removes` span that is not the rewrite itself), so the spawn line counts unverified removals too. Wait for one return per spawned page (`<page>: verified <n>; none <a> material <b> unresolved <c>`). Then run the Step 2 build again and read its verification lines: files read, ignored, verdicts applied (removals counted separately), items rejected. A rejected item names the record and the reason; fix the file or re-spawn that page, and the file written next is the whole page again, every candidate and both parts where both are required, because the build reads the file in hand and no earlier file. A file ignored for a wrong `sourceHash` was written against another version of the page and leaves that page's records `stale`: delete the file and re-spawn the page. Continue when the build no longer names a page to verify and no verification line reports an ignored file.

## Step 4: Grade

Spawn one `GRADER` per page in `manifest.json`, plus one with items `set` when `triage.json` holds set-wide clusters, mode `seen`, all in one message. Each grader reads the rubric, the page and every cluster on that page, predicts the move with a heuristic id and one gated sentence, and writes `calibration/grades/<page>.json`. Wait for every one-line return and check the counts add up to the page's clusters.

## Step 5: Score

```
bash ~/trade-imports-arch-workspace/.claude/tools/editorial-triage/grade-triage.sh score --dir ~/trade-imports-arch-workspace/.claude/workareas/editorial-triage/<run>
```

The score is the rubric's process measure: the share of grades predicting `R`, `C` or `W` among graded clusters, with the load (`K`, `O`, `T`), the share ignored, overall and per page, and the run's mode and intent. Compare two scores only for one document set under one intent, and read a change in the share with the findings that produced it; the score alone establishes neither that the review improved nor that the rubric or the brief needs work.

## Step 6: Plan and spot check

```
bash ~/trade-imports-arch-workspace/.claude/tools/editorial-triage/grade-triage.sh plan --dir ~/trade-imports-arch-workspace/.claude/workareas/editorial-triage/<run> --sample 10
```

`closing/plan.md` is the report: Apply (`R`, `C`, `W` with the text each edit needs; a replacement that spans lines as an indented block; a removal the verifier judged `material` with its note under the line, because the user reads what the deletion loses before it applies), Decide (`K` with both statements and the default side; `T` with the instruction needed, including every entry held from Apply because its edit has no verdict, a verdict of `material` or `unresolved`, a stale page or an unsupported introduction, with the record's changes and introductions under the line), Presentation (each `presentation` cluster with its actors and steps, for its owner; never an Apply entry, whatever the label or grade), Open (`O` lines with owners), Retained (passages the reviewers found adequate), Ignored (a count) and Problems (clusters the plan cannot close, with the reason). Show the user the Spot check section verbatim: ten apply entries with before and after, and the verifier's note where a removal carries one. One veto halts the batch. Turn the veto into a rubric heuristic through the Calibrate loop below, re-grade the page it came from, re-plan with a new `--seed`, and spot-check again. Zero vetoes releases the batch.

## Step 7: Apply

A run whose `mode` is `review` ends before this step: apply refuses such a run under every flag, naming the mode, and that refusal is the run's normal end and not an error to work around. A review-mode run returns findings, retains and questions, and the review is re-run in `revise` mode when the user wants the batch applied. Go to Step 8.

```
bash ~/trade-imports-arch-workspace/.claude/tools/editorial-triage/grade-triage.sh apply --dir ~/trade-imports-arch-workspace/.claude/workareas/editorial-triage/<run> --dry-run
```

Before any page is written, under every flag, apply re-checks each entry against the run and the page as they stand now and skips it with the reason when the cluster now holds a `presentation` finding (`skipped-held`), the record no longer proposes the entry's edit, span, text or hash (`skipped-changed`), the edit has no verdict (`skipped-unverified`), the verdict is stale (`skipped-stale`) or refuses the move (`skipped-held`), or the page is neither the one the review read nor the one apply last wrote (`skipped-stale`). The dry run lists what would apply and what skips, those states included and a phrase absent from the page or present more than once. Then apply for real, adding `--force` only when the user has said the working tree's uncommitted edits under the pages are theirs. Never add `--no-spot-check`: that flag turns off the refusal that Step 6 exists to arm, the user's approval of the spot check is what licenses this step, and apply refuses the flag itself while a `material` removal is going to apply. A page apply writes is recorded in `closing/applied.json` with the hash of the file as written, so the next run accepts it; an edit made by anyone else makes the page stale until the review is re-run.

```
bash ~/trade-imports-arch-workspace/.claude/tools/editorial-triage/grade-triage.sh apply --dir ~/trade-imports-arch-workspace/.claude/workareas/editorial-triage/<run>
```

Each changed page runs the prose gate; an entry on a failing page carries `gate-fail` and the exit code is 2. Run the docs repo's own validation next (the command its CLAUDE.md names), then show the user `git diff --stat` and the diff. Never commit; the user commits.

## Step 8: Present what is left

Show the user the Decide, Presentation and Open sections of `closing/plan.md` verbatim, then the Ignored count and the Problems list. In review mode the run ends here: the plan's sections are the deliverable, and no `K` or `T` edit is made by hand either. In revise mode a `K` or `T` answer is an edit the `editorial` skill makes by hand, since the apply step covers `R`, `C` and `W` only; an `O` line goes to its owner outside this skill, and a Presentation entry goes to its owner with its actors and steps. Finish with one cold-reader pass over the changed pages, as the `editorial` skill's review path describes.

## Calibrate: build the grader from walked samples

Run this before tuning rules or changing the review upstream, and whenever the user's verdict on a run is "too much" or "not sure it is right". The grader is the shared definition of how a finding is closed; the rubric holds that definition. Rubric: `assets/grading-rubric.md`. Worker: `references/GRADER.md`.

1. Draw a round of ten items, evenly across the tool's categories, from a built run:

```
bash ~/trade-imports-arch-workspace/.claude/tools/editorial-triage/grade-triage.sh sample --dir ~/trade-imports-arch-workspace/.claude/workareas/editorial-triage/<run> --round <n> --size 10
```

Pass `--targets` when the run's categories are not the ones the defaults budget for, and pass the same value on every round, because the targets are cumulative and a category the flag does not name is budgeted 2. A run weighted toward removal, such as a review whose intent was `distil`, puts most of its clusters in `propose/removal` and `propose/tangent`, so the defaults spend the sample elsewhere and later rounds exhaust. For such a run: `--targets '{"propose/removal": 8, "propose/tangent": 8, "fix/verified": 6, "discard/tangent": 3}'`.

2. Show the user the cards in `calibration/round-<n>.md` verbatim. From round 2 onward, spawn a `GRADER` first in `blind` mode on the round, so the round is unseen when the grader grades.
3. Take one entry per card from the user: the card number, one closing move (`R` remove, `C` correct, `W` reword, `K` keep one side as `K:A` or `K:B`, `O` record as open with an owner, `I` ignore for now, `T` tell me what to do, which needs the instruction as its note) and an optional note in their words, for example `2 R; 3 R cut the mechanism, keep the requirement; 10 O`. A `T` instruction and every note become candidate heuristics. Record them:

```
bash ~/trade-imports-arch-workspace/.claude/tools/editorial-triage/grade-triage.sh label --dir ~/trade-imports-arch-workspace/.claude/workareas/editorial-triage/<run> --round <n> --labels "<entries>"
```

4. Measure agreement between the grader and the user on the round, and read the disagreements:

```
bash ~/trade-imports-arch-workspace/.claude/tools/editorial-triage/grade-triage.sh agree --dir ~/trade-imports-arch-workspace/.claude/workareas/editorial-triage/<run> --round <n>
```

5. Turn each disagreement, and each note, into a rubric heuristic (`H-<nn>`, with the items that produced it) in `assets/grading-rubric.md`. A heuristic must hold for any technical document; a rule that only fits the document set under review is a run note for the review workflow, not a rubric entry. In round 1 the grader runs after the labels, to check the first rubric; in later rounds it runs blind before them.
6. Stop when two consecutive rounds reach move agreement of at least 0.85, or when the user says the heuristics are settled. Then grade and score the whole run (Steps 4 and 5); that score is the baseline every later change to the rules or the review brief is measured against. Nothing in the pages changes during calibration.

## Scripts cheat-sheet

All under `~/trade-imports-arch-workspace/.claude/tools/editorial-triage/`:

| Script | Purpose |
|---|---|
| `build-triage.sh` | Normalise a version 3 review result (`lib/normalize-v2.jq`) into records and retains, resolve anchors, gate rewrites, nominate claim changes (`lib/claim-elements.jq`), apply the verdicts in `verification/`, cluster, partition and rank; `--hash-pages` prints the pages' hashes for the review workflow's snapshot |
| `grade-triage.sh` | Calibration: `sample` a round of clusters as cards, `label` the user's move per card, `agree` the grader against the labels, `score` a whole run. Closing: `plan` the move that closes each cluster with a spot check, `apply` the R, C and W entries to the pages after re-checking each against the current run and page (`--dry-run`, `--moves`, `--force` for a dirty tree, `--no-spot-check` which the skill never passes; refused in review mode) |
